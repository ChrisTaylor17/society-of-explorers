# Android email-link transport

This source milestone adds an optional `supabase-email-pkce-v1` channel to the existing Android member module. Older modules retain their existing password sign-in behavior. The email channel never writes an ordinary provider session or selects a member account.

The bridge exposes `prepareEmailLink`, `pendingEmailLink`, `claimEmailLink`, `discardEmailLink`, and `sendEmailAuth`. Native results enter JavaScript as untrusted envelopes and are parsed by `native-auth-ports.ts`. Provider origin and publishable key remain trusted public build configuration. The callback is derived from the installed application ID: `<applicationId>.email://auth/callback`, with a protected, random `flow` query value. Debug and embedded application-ID suffixes therefore receive distinct callback schemes without another configurable redirect target.

`EmailLinkSession.kt` generates a 32-byte verifier with `SecureRandom` and its SHA-256 S256 challenge. Only the challenge, exact redirect target, email, purpose, flow ID, phase, and timestamps leave native preparation. The verifier and captured code occupy a reserved entry in the existing encrypted, no-backup account store. Generic `session`, `pkce`, and `user` slot operations cannot address that entry. Current-namespace reset clears it with the same durable storage-generation transition.

Preparation deliberately replaces the prior flow. One prepared flow permits one explicit signup, confirmation resend, or recovery request according to its purpose. Resend uses `/auth/v1/resend`; it does not repeat signup with another password. Request bodies have exact keys, canonical compact ordering, a 16 KiB ceiling, empty signup metadata/security objects, and the native challenge. No automatic transmission or retry occurs during preparation or callback capture.

The MainActivity handles both cold and warm callbacks. It removes the Intent data and clip data before React/Linking delivery. Capture accepts only the configured scheme, `auth` host, `/callback` path, a matching started flow, and a single bounded code or provider-error result. Unknown or duplicate query keys, fragments, mismatched flows, and a second callback for an already captured result are refused. Provider-error text is not retained or displayed. Callback capture performs no network request and creates no signed-in authority.

An unclaimed flow expires one hour after preparation. A captured code has an additional five-minute local deadline. Explicit claim atomically removes the durable verifier/code before returning either secret. The memory-only claimed scope permits one PKCE exchange, one exact exchanged-token user check, and—only for recovery after the subject check—one password update. The native response guard requires the literal `recovery` or `email/signup` AMR purpose, matching token/user subject, and sufficient token lifetime. The claimed scope expires at the earlier pending/code deadline; after exchange it is also bounded by the access-token expiry minus two minutes. These local deadlines do not establish provider code validity or email delivery.

Preparation, pending reads, claims, and sends check native online state and capture the native foreground epoch before the single-worker queue. Queued execution rechecks online state under the connectivity lock before taking the foreground lock, keeping accepted mutations and enqueueing ordered against both native network observations and Activity retirement. A delayed JavaScript screen event cannot obtain fresh email authority while the native state is already offline or unknown. Background, offline/unknown connectivity, module invalidation, expiry, replacement, and account reset retire claimed memory authority and cancel its tracked requests. Backgrounding preserves unclaimed protected pending state so opening an email app does not require an automatic exchange on return. Exact-generation, exact-flow discard remains a local-only operation while inactive; an old discard cannot delete a newer flow. JavaScript retirement also attempts direct discard for a known claimed flow.

Email requests reuse the existing opaque generation-bound handle, 15-second deadline, single physical transmission guard, redirect refusal, cookie-free client, strict UTF-8 decoding, and 1 MiB response bound. The ordinary member and password-auth path allowlists remain separate. Cancellation cannot undo an already transmitted email request or password write. A lost password response remains uncertain; later acceptance does not prove an earlier sent password write cannot still finish. Ordinary explicit password sign-in is the subsequent account-entry path.

The focused receipt is `verification/web/evidence/native-email-bridge-policy.json`: 33 passing tests, comprising two new executable TypeScript adapter cases, seven new static native source-policy checks, and 24 existing adapter/auth/keyed checks. The latter overlap other milestone receipts. Scoped lint passed. Its selected input hashes and exact clean-environment commands are recorded in the receipt; it does not claim a complete dependency closure.

Android Codegen, Kotlin compilation, installed callback delivery, Keystore behavior, and device lifecycle acceptance remain unverified. No SDK/toolchain downloads, provider configuration, email sends, or production calls were made. This is a custom scheme, not a verified App Link; S256 and the protected flow binding mitigate code interception, while provider redirect allowlisting and installed-device acceptance still need verification. The current native account module is Android-only. No iOS email-link implementation is claimed. Storage namespace changes caused by application ID, provider, or public-key changes expose a separate store; cleanup of historical namespaces is not established by clearing the current one.
