# Per-message consent decision ordering

This candidate repairs the web author permission workflow. Native and Quest author consent controls and human reviewer parity are unchanged; this milestone does not implement them. The original consent and allowance migrations remain unchanged, and the before-state SQL/browser reproductions remain historical evidence.

The reproduced defect was an accepted unchanged choice leaving the revision unchanged: an older held opposite request could still commit after the newer confirmation. The additive `circle-message-ai-consent-intent-preflight.sql` → `circle-message-ai-consent-intent-apply.sql` candidate consumes exactly one consent revision for every accepted decision, including keeping an absent permission off or keeping an existing permission unchanged. A request with an old revision, wrong current message hash, wrong policy or invalid author cannot commit. Safe-integer exhaustion refuses both directions. Legacy messages remain excluded until a fresh explicit author opt-in; a GET never creates consent.

The HTTP body is still exactly `{expectedConsentRevision, contentHash, policy, allowed}`. Actor authority comes from the canonical authenticated member, never from that body. Successful replies must contain the same Circle/message/hash/policy/choice and exactly the submitted revision plus one. A lost committed response followed by an exact old retry receives a conflict; this is not an idempotent receipt API. A higher current GET can establish current permission, without establishing which earlier delivery completed. An unchanged GET cannot prove that a held request will never finish.

The mounted web panel retains uncertain intent conservatively and allows only an explicit reviewed decision to settle it. Background, offline and account changes retire rendered authority. Actual Contributions unmounting destroys that panel's local memory; the remounted panel therefore explains that an earlier request may still complete and offers a fresh explicit choice even when the current value is already off. There is no durable queue, automatic replay or delivery guarantee.

## Installation and containment

This is an unapplied review candidate. Install the original per-message consent and allowance candidates first, then this successor. The old allowance preflight deliberately requires the original invoker snapshot; do not re-run it against the successor. The fixture runs the current Circle publication/coverage chain plus this candidate, while a separate lean fixture preserves and checks the original consent baseline.

Preflight pins the exact owned consent table, constraints, column defaults, indexes, RLS state, grants and lack of policies/custom triggers/rules/inheritance. It pins all three consent function bodies/signatures/attributes, their current owner and service-only execution, and all four direct/transitive authorization/hash helpers. Unexpected overloads, definitions, column privileges, role inheritance or browser/service schema creation rights stop application rather than being silently repaired. Apply rechecks after taking the consent table lock and preserves every recorded choice/revision and unrelated defaults.

All three consent functions become narrow, fixed-search-path `SECURITY DEFINER` routines owned by the reviewed table/function owner. State and snapshot bodies remain byte-for-byte unchanged. Their existing `FOR SHARE` locks require update privilege in invoker mode; preserving those locks while removing raw service writes is the reason for this change. The setter retains the original cohort → message → safety → consent lock order, author/hash/policy checks and visible-message enable restriction. Snapshot still checks current reviewer assignment/conflicts, current message hash, withdrawal and the complete-case bound, and returns only the one message's permitted text and revision metadata. No reporter notes are added.

The service role retains table SELECT and the narrow RPC calls; raw INSERT, UPDATE, DELETE and column writes are denied. PUBLIC, anon and authenticated cannot call the consent functions or access the table. Allowance remains disabled/zero unless the owner separately authorizes a finite synthetic or production window; this migration neither activates it nor calls a provider. Fixed search paths and narrow function grants follow the [Supabase function guidance](https://supabase.com/docs/guides/database/functions) and [PostgreSQL function privilege guidance](https://www.postgresql.org/docs/current/sql-createfunction.html). Existing locks remain transaction-scoped as described in the [PostgreSQL locking reference](https://www.postgresql.org/docs/current/explicit-locking.html).

## Disable, recovery and acceptance limits

The disable-only rollback revokes the setter's service execution and preserves current state/snapshot reads, rows, revisions and the raw-write barrier. It does not revoke previously granted author consent, disable an independently configured allowance, delete history or restore the old unsafe writer. Explicit reapply accepts only the recognized installed/disabled definitions and restores the safe setter. Coordinate trusted-owner function/role maintenance separately; the local proof does not establish concurrent administrative DDL safety.

Roll out the matching migration, strict receipt route and web recovery UI together. Keep web permission changes unavailable during a partially upgraded deployment. A strict current route refuses an old same-revision successful no-op reply as unavailable; it cannot make old database semantics safe by itself. Do not downgrade to the original setter or restore raw table grants.

`verification/web/evidence/consent-intent-backend.json` binds the focused SQL/actual-handler/parser checks, runtime hashes and logs. `consent-intent-browser.json` separately binds the current web interactions. Tests use disposable cached PGlite, synthetic actors/PostgREST delivery and the actual current handlers/SQL; no provider request, live row, production schema change, install or deployment is involved. PGlite has one backend: sequential CAS, held HTTP dispatch, rollback and privilege denials are proved locally, while independent PostgreSQL sessions, hosted schema cache, restored production grants, load and device behavior remain unverified. The November 4 Supabase CLI changelog was reviewed; no CLI was invoked or installed for these local SQL candidates.
