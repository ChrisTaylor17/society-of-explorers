# Thinker award accounting

This local milestone replaces the Thinker route's separate event INSERT and increment RPC with one atomic, idempotent award transaction. Its SQL is **unapplied**. It does not change the three captured legacy reward definitions, their containment scripts, deployed accounts, or production access.

## Request and result contract

Every authenticated `POST /api/thinker` requires a `requestId` UUID. The four current authenticated callers create a new key for each deliberate request. The demo-only homepage remains unchanged. There is no automatic POST retry. Reusing a key is permitted only for the exact same normalized request; changing the key creates a different award opportunity. This is not abuse prevention or a reward budget.

The route derives the member once from the verified session. It hashes the normalized thinker, message, reaction flag, salon, council mode/context and community with a version tag. Only the digest is stored in the receipt; no prompt, profile text, identity subject or provider response is persisted there. Body-supplied member IDs and amounts have no award authority.

After a successful non-silent provider completion, `soe_thinker_reward_award(p_actor uuid,p_request_id uuid,p_request_hash text,p_thinker_id text,p_is_reaction boolean)` locks that member's current row. A new award increments `coalesce(exp_tokens,0)` by a fixed 8 (conversation) or 4 (reaction), inserts one existing `exp_events` row, and records its receipt in one transaction. An event/receipt constraint or integer-overflow failure rolls the transaction back. The planned profile revision guard does not treat EXP as an authored profile change.

The new private table `soe_thinker_reward_receipts` has primary key `(member_id,request_id)`, a unique event FK, the normalized request digest, thinker/kind/amount and timestamp. Receipts are retained; deleting them destroys the replay guarantee. They do not expire or reset. Exact replay returns the same event and original amount without another credit. A different hash, thinker or kind under a used key raises SQL `PT409` before any accounting writes.

The service RPC's exact four-field receipt is `{requestId,amount,eventId,replayed}`. The actual route validates all fields and binds the key and expected amount. A confirmed stream completion includes `reward:{status:'confirmed',...receipt}` and legacy `expAwarded` of 8/4 on the first credit or **0 on replay**. An error, thrown/lost response, mismatched key/amount, malformed receipt or eight-second confirmation deadline yields `reward:{status:'unknown',requestId}` with **no `expAwarded` field**. It never overwrites a balance from the old auth snapshot. Because SSE has already started, SQL `PT409` is reported as an unconfirmed reward inside HTTP200 SSE; this is not an HTTP409 endpoint contract.

`GET /api/thinker?requestId=UUID` is a separate own-member receipt check. It verifies a fresh actor once, accepts exactly one query parameter, checks same-origin/cross-site metadata and returns private/no-store JSON. It calls only `soe_thinker_reward_receipt(uuid,uuid)`, with no provider, messages, action execution, event insert or credit retry. A valid matching receipt returns confirmed with `replayed:true`; absence returns unknown. Missing receipt is **not proof that an in-flight transaction cannot commit later**. Service failures or malformed readbacks return503 unknown.

## Member experience and lifetime

The Council, member conversation invitation, salon hub and Waddle thinker flows pass a logical request key and display the shared `ThinkerRewardNotice`. It shows pending, confirmed original amount, or an explicit unconfirmed result. “Check reward only” makes a deliberate GET with fresh selected-account headers, no redirects/referrer and an eight-second whole-operation deadline. Confirmation and replay do not increment any client balance. Unknown results are never displayed as zero credit or success, and no button automatically repeats the model request.

The hook retains at most32 unresolved IDs in the mounted page and blocks a new request at that bound. The member can check or explicitly dismiss an earlier result. IDs are not stored in localStorage or restored after reload; copy an unknown request ID before leaving if follow-up is needed. A dismissed result does not cancel or reverse a possible credit.

Canonical deliberate provider selection and `signOutBrowser` emit the existing same-tab/cross-tab retirement event; sign-out emits before its first await. The hook immediately clears results, aborts checks and advances an epoch so held JSON/late SSE cannot restore old receipts. It unregisters on unmount. This hook adds no SDK creation/subscription; unsolicited SDK-only events outside that existing notification contract are not independently covered. The GET remains server-authenticated and actor-scoped.

## Migration and authority

The single new candidate is `docs/sql/thinker-reward-accounting.sql`. It refuses name collisions and unreviewed owners, administrative/inherited browser/service role authority, browser schema creation, or missing observed table/key/service prerequisites. It adds one RLS-enabled table and two SECURITY INVOKER functions with a fixed search path. It scrubs all non-owner new-object default ACLs, including unrelated roles, then grants service SELECT/INSERT on receipts and EXECUTE on the two functions. Browser roles receive no access; service cannot UPDATE, DELETE or TRUNCATE receipts. Existing tables, profile guard, reward bodies, current_prompt helper/policies, global defaults and prior containment grants are unchanged.

Service is a trusted server boundary: it already has member/event write authority and the new receipt INSERT grant. This design does not protect against a compromised service role or owner-issued receipt deletion/DDL. Role/DDL maintenance must be coordinated. Row locks and atomic transaction semantics are exercised locally; one PGlite backend does not prove an independent concurrent PostgreSQL schedule. An independent connection test remains a deployment acceptance gate.

Deploy only with separately approved schema/caller review and a coordinated rollout: old authenticated clients without the UUID now receive400. No legacy server-generated key fallback is provided. The dated live `exp_events` schema is represented by exact known column types/defaults/PK/FK semantics; the saved helper explicitly labels unknown FK name/actions, unrelated profile columns/identities and synthetic closed browser table ACLs. No full database restore or hosted PostgREST acceptance is claimed.

For operational withdrawal, stop the coordinated new caller/server path and review service EXECUTE removal separately. Preserve all receipts/events/balances. Do not DROP a used receipt table, reverse reward rows, restore the stale-overwrite route, or run a CASCADE rollback. There is no automated data rollback or “unused” claim. Production application, remote permissions, backups and receipt-retention policy require owner approval.
