# Circle hosting across web and native

Local implementation and verification candidate. Production release remains on hold; the SQL candidates have not been applied to a hosted database. See the current [release status](../../RELEASE_STATUS.md), [membership intent migration](circle-membership-intent.md), and [production migration plan](production-migration-plan.md).

## Member experience

The native member account now offers **Start a Circle** when its hosting connection and request-ID service are available. The existing web Start a Circle page uses the same normalized creation contract. Both check the current canonical member before presenting hosting access, reviewing a listing, or sending a confirmed request.

Hosts choose an in-person, online, or hybrid format; a public venue and optional location; a weekly weekday, local time and time zone; a start date within 180 days; and a group size of 3–12 including themselves. Public fields, the derived first meeting date, the private HTTPS meeting link and the reading plan appear in the review. A separate confirmation creates the free Circle and its first host membership. Hosting responsibility stays attached to the host after leaving.

The reading plan can use the existing twelve-week path or one of eight pinned editions with 1–12 explicit inclusive weekly ranges. Native hosting loads source metadata anonymously, verifies the exact edition and range boundaries, and shows attribution, source headings, license notices and rights limits. A deliberate **Read week selection** opens the existing bounded text reader; opening a selection carries no member or Circle identity. The reader still identifies tables and nontext content as gaps rather than reproducing complete source layout. Rights outside the United States remain unassessed.

A matching creation receipt is followed by a current Circle read that verifies host access and a sufficiently recent revision. Native hosts can then open **My Circles** and explicitly load their groups, or choose **New Circle draft** and check hosting access again. Creation is limited to three active hosted Circles and the existing separate daily creation quota. List absence or a quota count cannot settle an uncertain creation request.

Native Circle detail and the membership-management fallback now offer a separate completion review to current hosts, including hosts who have left and hosts of hidden or unusable listings. Completing permanently closes new joins and attendance responses; it preserves existing discussion access, membership exit and authored contributions. It neither transfers hosting nor restores membership. There is no reopen action.

## Account, request and lifecycle boundaries

`lib/circles/hosting.ts` defines normalized, exact-field creation and completion bodies, owner-aware hosting-access responses and owner-aware receipts. Creation and completion require `expectedMemberId` in the body. Their server handlers compare it with the authenticated canonical member before dispatching SQL. Web hosting also sends the existing expected-member header on relevant reads. Old ownerless creation/completion callers fail closed and must be updated as part of a coordinated rollout.

Native creation uses a controller retained by the owned member connection. It pins the verified provider subject and canonical member. Background, blur, offline, disconnection and failed verification clear displayed drafts, private links, source metadata and review authority. They do not automatically check access or retry. A sent uncertain request survives privately within that owned connection, with identical normalized bytes and request ID. Returning requires fresh same-account proof, a new review of the exact request and confirmation. A refused retry does not establish that the original request failed. Current dates and quotas cannot prevent an exact accepted request from reaching the SQL receipt lookup, although unavailable source verification can still refuse a request without settling an earlier outcome.

Changing members discards the old member's retained hosting controller. Terminal Close discards local retry information and warns that an already-sent request may still finish. Retention is in memory, not a persistent queue or recovery guarantee after process termination. Native Directory completion retains its existing participation lifecycle: retirement discards local retry details and already-sent changes may finish. Its ordinary same-view uncertain retry preserves the exact request.

The new membership-intent SQL advances the Circle revision once for every newly accepted join or leave, including a request that does not change a membership row. Exact receipt replay does not advance it. This prevents an earlier delayed opposite action from overriding a later accepted intent. The server and native Directory require join/leave receipt revisions above the reviewed revision; completion retains its existing terminal semantics and revision floor. Historical no-op receipts can remain uncertain until newer state is available. See the migration document for preserved history, rollout order and disable-only rollback.

## Verification boundaries

Focused controller, transport, server and SQL tests run against cached local runtimes. Browser composition uses actual application components and canonical handlers with local PostgreSQL-compatible SQL; provider identities, OS services, network delivery and native primitives are explicit test doubles. Final counts, source bindings and evidence hashes are recorded in the [hosting verification receipt](circle-hosting-verification.json).

The November 9 native follow-up gives an uncertain completion its own heading, explains the effect of completion, and labels the action **Retry exact Circle completion**. It explicitly resends the same completion request; it is not a read-only status check. The existing confirmation guard, callback, request retention and lifecycle clearing are unchanged. This view-only change passed single-file TSX transpilation and diff checks; it has not been newly rendered on a phone or included in the existing Android APK. [Change and verification limits](/Users/christaylor/Documents/Mewest/RESEARCH/native-completion-retry-2026-11-09/README.md).

No hosted database changes, deployment, provider requests, API keys, paid usage, dependency downloads, native compilation, signing or physical-device acceptance are established by these local checks. Kotlin transport checks are static unless a separate compiled acceptance result is recorded. Portable and web type-check configurations exclude native TSX; the screens are transpiled and browser-composed here, without a complete React Native type check. The legacy jsdom suite remains unrun because its cached runtime is offloaded; Chromium component proof is reported separately.
