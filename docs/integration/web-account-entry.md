# Browser account entry

The account screen has separate email sign-in, account creation and confirmation resend forms. Changing mode, leaving the page or going offline clears credential fields and retires the old form's callbacks. Opening Login does not look up or create a member. Google and wallet remain available from sign-in.

Email creation and resend use distinct, bounded requests with secure S256. A pending local verifier binds the confirmation to a random flow, expiry and safe return path. The confirmation page removes callback credentials from the URL before constructing an isolated client. Continuing claims the verifier once under a browser lock, accepts only `email/signup`, verifies the exact token's user and discards the resulting session. Confirmation ends with deliberate ordinary sign-in. It never writes ordinary auth cookies or selects/provisions a member. Resend does not repeat account creation or change a pending password. An accepted email request does not prove delivery or account existence; an already-confirmed member can sign in directly.

Password sign-in uses the actual pinned AuthClient in memory. The candidate must have password purpose, a matching subject and a fresh exact-token user response. Only then does the actual SSR cookie helper publish the sanitized session. Ownership is checked after the helper's asynchronous read and immediately before each cookie write. Provider selection and canonical member readback must match the same account before navigation. Missing member setup is part of that explicit sign-in, not a mount effect.

A secure random browser intent identifies the current deliberate password, Google, wallet or logout attempt. Only browser code writes that current-intent cookie. The server's HttpOnly selection receipt binds the initiating intent, provider and verified subject. Cookie-based member resolution and provisioning require all three plus the real provider credential. A browser bearer request carrying an intent must also match its selected Supabase subject; cookie-free native bearer verification remains separate. Older cookie-only sessions require deliberate sign-in again.

Google uses the actual SDK's S256 authorization URL, an explicitly guarded verifier publication and a matching initiating-intent cookie. The callback checks those bindings before exchanging the code, buffers session cookies until OAuth-purpose and fresh exact-token identity pass, and sends the user to an explicit completion action. A stale completion cannot provision or navigate for a newer browser choice.

Wallet sign-in retains the injected Ethereum provider, actual ethers address handling and SIWE message construction. The server-signed nonce is bound to the initiating intent; the signed message must match the current origin and address. A wallet popup may move focus away: its result stays in memory and requires an explicit Continue on returning. Account/network changes, offline state, closure and expired operations retire the attempt. The selected member must match a fresh canonical member response before navigation.

The intent receipt is an ordering boundary, not an authentication credential. A delayed server response can still overwrite or clear a newer session cookie and cause denial of access. It cannot select the old identity while the browser's current intent differs. Requests already dispatched can finish after local retirement; aborting a view does not recall provider work or a membership insert. There is no server ledger promising global operation ordering, and the signed wallet nonce remains stateless within its short lifetime.

Verification uses cached SDKs, local browser composition, synthetic provider transport and explicit lower-level identity/database doubles. It does not establish real mail delivery, Google configuration, wallet-extension behavior, CAPTCHA/rate limits, deployed routing, production Data API/RLS, native compilation or device acceptance. No live provider account, issued credential, deployment, production SQL or spending is used by this milestone. Exact test and build evidence is recorded separately in the verification receipt.
