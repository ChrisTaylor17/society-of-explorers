## Public-space privacy follow-up

The finish review found that the anonymous list accepted `status=pending` and `status=archived`, and that direct-ID details returned full locations and annotations without sign-in or a status filter. This contradicted the member/host rules in [world permissions](../../lib/world/permissions.ts). The [list handler](../../app/api/world/spaces/route.ts) now accepts only active summaries, rejects alternate statuses, duplicate/unknown query keys and overlong city filters before creating an admin client, and uses a literal active-row predicate. The [detail handler](../../app/api/world/spaces/[id]/route.ts) requires a verified member and queries only active rows before any scan or annotation read. Pending/archived details remain unavailable; no private host-view path was invented. Existing POST, host PATCH and host DELETE functions are unchanged.

[Seven actual-handler groups](../../verification/web/tests/world-spaces-public-read.test.mjs) pass using the installed Supabase client with synthetic identity/HTTP boundaries: non-active list denial without any client, strict queries, coarse projection, anonymous detail denial, indistinguishable private/missing details with no secondary reads, member-visible active details, and generic failures. Together with the four controller groups, 11/11 checks pass; scoped lint is clean. No hosted data, schema, credentials or permissions were changed. These tests do not prove hosted RLS or production recovery. The service-role bypass behavior was checked against the [current Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).
