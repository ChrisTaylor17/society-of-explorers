# Native member entry

The existing Circle and MemberCircle TSX screens, verified-provider owner, host and native port adapters have been integrated into this package. `index.ts` registers the member-first `App.tsx`; it does not register the historical synthetic demo.

The authenticated native application composition supplies `App` with `{memberCircle: {origin, circleId, auth, transport}, connectivity}`. `auth` is its existing verifying Supabase Auth interface and `transport` must reject redirects before forwarding credentials. The trusted native-only connectivity port supplies synchronous `snapshot(): 'online' | 'offline' | 'unknown'` and `subscribe(listener): () => void`. It is a function/object injection from application code, never a launch-extra or global lookup. The component does not create an auth client, provider account, credential or global configuration. Android now has an app-local v2 TurboModule source implementation and explicit `prepareAndroidMemberBinding` helper; trusted application composition must still supply and own its account client. The native source has not been code-generated, compiled or run. Unconfigured builds show an honest unavailable state and perform no authentication or private reads.

The configured entry now requires an explicit member-account check before opening a Circle. A canonical unconfirmed-account response permits separately acknowledged member setup for the exact verified provider subject, looking up and reusing an existing record rather than assuming none exists; a matching fresh account readback and **Continue to Circle** are required before mounting the conversation. Unknown setup outcomes never retry automatically. **Close member view** retires local private views; it does not delete the member or sign out the provider account. The [existing-account setup milestone](../../docs/integration/native-account-setup.md) records nine actual-screen/browser stories against canonical account handlers and local identity SQL, with explicit provider/native doubles. This does not supply app-owned native sign-in or device acceptance.

The account-ready **View my contributions** entry opens a separate author view across Circles. It starts no list request until **Load my posted messages** is chosen and does not grant or require current Circle membership. Pages contain only owned messages; selecting one clears the list and checks current author controls before withdrawal. Unknown withdrawals block ordinary navigation until an exact manual retry confirms the receipt; **Close member view** always retires private state. See the [native contributions milestone](../../docs/integration/native-contributions.md) for the actual-screen/canonical-route/local-SQL proof and native acceptance limits.

Both the verified session owner and Circle host require active application state and validated online connectivity. Missing, malformed, failed or unknown connectivity stays closed. Lifecycle listeners are attached before connectivity sampling or authentication; registration-time offline events supersede a stale initial online snapshot, and Android blur survives an active-state resample. Native hosts start offline regardless of supplied host defaults. Existing non-native/Quest hosts retain their prior default. Offline/unknown events retire private reads, drafts and pending requests; reconnecting alone does not restore a view or retry work. Reconnection alone triggers no verification or fetch; the unchanged SDK `VERIFY_EVENTS` may reverify afterward while active and online, but no Circle read starts automatically. Check the member session and explicitly refresh Circle access. Replacing the trusted port creates fresh owner/host lifetimes; late callbacks and subscription-disposer events cannot revive the retired ones.

Complete archive and thread reads use the current canonical discussion endpoint and parser. The native discussion composer uses a fresh server preview, explicit confirmation and a secure request key for new root messages and replies to visible messages. Unknown outcomes retain the exact reviewed request for manual receipt checking or exact retry; nothing is retried automatically. Native message actions now use an explicit fresh-state check, report confirmation and author withdrawal disclosure. Unknown actions retain only the exact request for manual retry; a current-state read cannot confirm an earlier report. See [native message safety and validation limits](../../docs/integration/native-message-safety.md). This is source/browser-fixture integration, not compiled Android or device acceptance. All private views, drafts, previews and pending keys clear on identity changes, activity loss, offline signals and closure.

Trusted member composition must supply an asynchronous `newRequestId` function for keyed posting. The Android v2 bridge advertises `requestIdPolicy: 'os-random-uuid'` and generates a UUID inside its current storage epoch. The JS binding exposes it only when that exact policy and method are available; older read-only bridges have no key fallback. No Hermes/browser `crypto.randomUUID` or `Math.random` assumption is used by the native writer. This remains source-level integration until native Codegen, compilation and device acceptance are completed.

The historical Android project remains available for integration with synthetic application IDs and instrumentation. Its embedded synthetic build uses debug signing for local fixtures; release tasks reject default debug signing and require a reviewed external identity/signing descriptor. Unnecessary permissions and app-data backup were removed from the release policy, but actual binary/signing/backup acceptance remains unverified. There is no generated iOS native project. Expo exports are JavaScript/assets; they are not native binaries or store acceptance. See the [staged toolchain plan](../../docs/integration/native-toolchain-unblock.md).

`node_modules` links the existing native runtime without installing anything. Its offloaded dependencies currently prevent a verified full native typecheck/export. The portable controller types, real TSX server render with explicit React Native primitive doubles, and Quest browser integration are tested separately; those do not establish Hermes, native networking or device behavior.

The focused connectivity checks run actual App/MemberCircleScreen/CircleScreen/controller source in cached React/Chromium with explicit React Native DOM primitive/AppState, connectivity, identity and transport doubles. They cover unknown/offline startup, registration and lifecycle races, manual reconnect, held auth/JSON, replacement and unmount. Source-loader reads reject symlinks and nonempty zero-block files. The fixture explicitly selects materialized canonical web React; it does not hydrate the older linked native runtime. The Android source now registers secure transport/storage and OS connectivity implementations; compiled registration, actual OS behavior, the account owner and binary/device acceptance remain unverified. Local tests do not close those release gates.

The transport adapter observes late `begin()` completions after timeout or abort and attempts to cancel each valid allocated handle once, without sending after retirement. Synthetic bridge tests verify that behavior; they do not prove OS-level cancellation or compiled native registration.

The v2 storage contract carries a native persisted UUID generation on every slot operation and request allocation. Reset is one native operation with a generation receipt; durable recovery remains unverified. JavaScript owners sharing the exact approved origin/storage key retire together, including different module wrappers and held private replies. A failed or lost reset receipt leaves the old lifetime closed; only explicit fresh capabilities can establish a new ready generation. The Android adapter memoizes each module wrapper and resamples native connectivity on event notifications, so queued old online events cannot replace current offline state. See [Android source, durability design and acceptance gates](../../docs/integration/android-member-bridge.md).

The portable TypeScript configuration excludes the new React Native-dependent Android adapter/spec; it checks the portable v2 ports and controllers only. Seven adapter cases execute actual TypeScript against explicit synthetic native modules; twenty-one durable-port cases exercise epoch/reset races. Neither substitutes for Codegen or a typecheck against the pinned native runtime.

The keyed discussion continuation adds seven key-source checks (six actual JS cases and one static Android assertion) and expands the actual-screen Chromium fixture to twelve stories. Those browser stories include explicit root posting and visible-parent reply/receipt/exact-retry controls against a synthetic DTO transport. See [native keyed discussion scope and evidence](../../docs/integration/native-keyed-discussion.md).
