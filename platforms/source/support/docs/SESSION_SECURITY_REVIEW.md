# Session security review and isolated fixes

This review used only non-issued fixtures and the previously isolated, unregistered native binding. Five baseline tests reproduced: (1) a mutable cached session could cause the bearer returned after verification to differ from the token supplied to verification, (2) a cached subject mutation could make an initial check promote a different subject, (3) a storage read already in flight could return its value after retirement, (4) synchronous sign-out while attaching a subscription could be followed by stale session promotion, and (5) a synchronous stop during attachment could leave the returned subscription uncollected. Two more tests independently reproduced a reentrant checking-observer sign-out being overridden by the continuing check or a queued recheck.

The candidate snapshots the checked token and subject, rejects mutation before promoting or transmitting, fences the result of a retired storage read, and protects subscription attachment and state transitions with lifetime/generation checks. Reentrant auth callbacks retain their enclosing callback state. Regression tests cover the outcomes and an in-process Circle host boundary.

These are conditional bugs in an isolated client prototype demonstrated with mutable/mocked provider data and synthetic callback timing. The review does not establish that the live provider exhibits those timings or that production was exploitable. The bridge remains unimplemented/unregistered and its capabilities are self-reported; provider auth networking and native secure storage remain unverified. Revocation and server-side authorization are separate requirements. A session replaced invisibly without an auth event or mutation of the returned object is not detected by the new snapshot check. An already-started native storage write or sent network request may still complete after retirement. No production identity or security clearance is implied.

Historical baseline finding, addressed in the account-handover candidate: explicit `removeItem` was allowed on a retired adapter. With two adapters sharing a bridge and storage key, an old adapter can delete a newer adapter's session after the new value is written. `evidence/retired-delete-review.log` demonstrates this with a fake bridge. Do not assume the FIFO queue identifies an account owner or prevents this stale deletion. Account-switch cleanup needs an explicit ownership/generation or storage-namespacing contract and native persistence tests; the local candidate implements an explicit in-process barrier, with durability and cross-process coordination still unresolved.
