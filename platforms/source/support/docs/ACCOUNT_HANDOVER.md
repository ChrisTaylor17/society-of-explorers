# Account handover and logout: local prototype

A retired adapter can no longer call `removeItem` or initiate a reset. A queued deletion that times out before it starts is skipped. A deletion already started remains in the shared FIFO until completion, so same-lane writes cannot overtake it.

For an intentional account change or local logout, call `resetAccountStorage()` on the current **open** binding before calling `close()` or constructing the next auth client. The operation synchronously increments the in-memory generation, blocks storage, aborts tracked requests and retires all registered bindings sharing the same bridge object and storage key. It waits behind already-started native storage operations, then removes session, PKCE, and user slots in order. Only successful completion before the deadline releases quarantine. Prior adapters remain invalid after success. The app can then create a fresh binding and client.

If cleanup fails or times out, access stays quarantined, even if late native operations finish. A fresh `createNativeMemberPorts` using the **same bridge object and key** can call `resetAccountStorage()` to retry; create a new binding and client only after success. The old binding is already closed. Errors are generic. This clears local storage only: it does not revoke provider sessions or sign out the account server-side.

The protection is intentionally limited to one JavaScript process and the same bridge object and key. Separate bridge proxies, different processes, app restarts or crashes do not share this generation or quarantine. A durable, native ownership/generation record and atomic cleanup/recovery protocol are required before production. Session/network calls already handed to native may still complete despite cancellation. A caller that starts a new account without invoking the barrier can still read previous data. The native bridge, provider traffic and secure storage remain unimplemented and unverified on devices.
